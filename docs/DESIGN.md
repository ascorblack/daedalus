# Daedalus — дизайн

Дата: 2026-09-06 (обновлено после решений владельца, см. `DECISIONS.md`). Статус: принятый дизайн.

Репозитории: бот — `ascorblack/daedalus` (это репо); ядро — `ascorblack/protocore-exp`
(копия protocore-community).
Бот — **личный агент одного пользователя**, который любой поднимает на своём сервере со своими
моделями; мультитенантности нет.

## 1. Что даёт ядро и чего в нём нет

`protocore` 2.0.0a3 (community, MPL-2.0, Python ≥ 3.12) — это **только ReAct-цикл**.
Все внешние вещи — `Protocol`, которые реализует «хост»:

| Контракт | Файл в ядре | Что нужно написать в Daedalus |
|---|---|---|
| `ILLMProvider` | `protocore/contracts/llm.py` | адаптеры провайдеров (в ядре их **ноль**) |
| `Tool` / `IToolRegistry` | `protocore/contracts/tools.py`, `tool_registry.py` | все инструменты (exec/read/write/…; в ядре только `AskUser` и память) |
| `ISessionStore`, `IRunStore`, `IEventStream`, `IBlobStore` | `protocore/contracts/*` | хранилища (SQLite + файлы) |
| `ISkillStore` | `protocore/contracts/skills.py` | скиллы как каталог `SKILL.md` |
| `IAgentDispatch` | `protocore/contracts/agent_dispatch.py` | саб-агенты (запуск второго `QueryEngine`) |
| `IWorkspace`, `IMemory` | `protocore/contracts/workspace.py`, `memory.py` | рабочая область и долгая память |

Точка входа: `QueryEngine(config=QueryEngineConfig(...), llm_provider=..., tool_registry=..., ...)`,
`engine.run(message)` → `AsyncIterator[TurnEvent]` (~55 типов событий, Anthropic-подобные).
`engine.snapshot()` даёт возобновление после рестарта — это ключ для self-restart.
`AskUserTool` переводит цикл в `AWAITING`, хост возобновляет с ответами — это кнопки/ответ в Telegram.

Вывод: Daedalus — это «хост» в терминологии ядра. Тонкий Telegram-транспорт сверху, а
основной объём — адаптеры. Это же означает, что агент, дорабатывая себя, будет менять
в основном хост-код (свои тулы, провайдеры, промпты), а ядро — редко.

## 2. Режим общения: решение

**Гибрид: Telegram-топики как сессии + Mini App как панель.** Не «или».

Почему не чистый текст: несколько параллельных агентов в одном приватном чате
превращаются в кашу; 4096 символов — не место для диффов, логов, списка сессий.

Почему не чистый Mini App: Mini App **не получает push**, живёт только пока открыт,
SSE/WebSocket умирают при сворачивании. Уведомления, файлы и вопросы агента всё равно
должны приходить обычными сообщениями бота — иначе задачи, идущие часами, теряются.

Схема:

- **Приватная супергруппа с топиками** («Daedalus»). Один топик = одна сессия =
  один рабочий каталог = один `QueryEngine`. Бот сам создаёт топик по `/new <название>`
  (или из Mini App), закрывает по завершении. Так работает ccgram — проверено.
- **General-топик = операторский канал.** Команды `/new`, `/status`, `/model`, `/restart`,
  `/rollback`, `/panic` обрабатываются **до** передачи текста агенту.
- **В топике**: одно «живое» статус-сообщение (модель, текущий тул, токены/стоимость,
  изменённые файлы), редактируется ≤ 1 раз/сек; итоговый ответ — обычными сообщениями
  с разбиением по границам блоков кода, длинное — документом; файлы — `sendDocument`;
  вопросы `AskUser` — inline-кнопки.
- **Mini App** (кнопка меню бота): список сессий с состоянием, транскрипт сессии,
  просмотр диффа перед применением self-change, хвост логов, файловый браузер
  workspace, настройки (модель по умолчанию, лимиты). Открывается из любой точки,
  восстанавливает состояние с сервера при каждом открытии, ничего не стримит долго.

## 3. Архитектура контейнера

```
docker: ubuntu:24.04 + uv + python 3.12 + git + node (для Mini App) + инструменты
├── /opt/launcher/            НЕИЗМЕНЯЕМО (COPY в образ, PID 1). Супервизор.
├── /srv/daedalus/            git-репо бота (mutable, монтируется томом)
│   ├── daedalus/             хост-код: transport/, host/, tools/, providers/, stores/
│   ├── miniapp/              Vite SPA
│   ├── skills/               SKILL.md-каталог
│   ├── GOVERNANCE.md         «конституция» — путь закрыт для записи тулами
│   └── tests/
├── /srv/protocore-exp/          git-клон protocore-community (mutable, pip -e)
├── /srv/workspaces/<session>/ рабочие каталоги сессий
└── /srv/state/               sqlite (sessions, runs, events), blobs, snapshots, last-good
```

**Супервизор** (`/opt/launcher`, ~200 строк, никогда не редактируется агентом):

1. запускает `daedalus` как дочерний процесс, держит health-канал (unix socket);
2. по сигналу «restart» от бота: `git -C /srv/daedalus rev-parse HEAD` → preflight
   (`python -m compileall`, импорт пакета, парсинг конфига, `pytest tests/smoke`) →
   если ок — `exec` новой версии и тег `good/<n>`; если нет — откат на последний
   `good/*`, перезапуск, сообщение в General-топик с логом ошибки;
3. держит лимит расходов (USD/сутки, токены/задача) — агент не может его поднять;
4. `/panic` — синхронно убивает всех потомков, не спрашивая агента.

Так у агента есть право сломать себя, но не право стать недоступным.

## 4. Self-develop: Pull Request → merge → rebuild

1. Задача от оператора («добавь тул для X», «обнови ядро до апстрима»).
2. Агент правит `/srv/daedalus` или `/srv/protocore-exp` в ветке, гоняет тесты, коммитит и
   **открывает PR** через `gh` (PAT только на два репо, см. `GITHUB-ACCESS.md`).
3. Бот шлёт в General-топик описание изменений + ссылку на PR с кнопками
   **Одобрить / Отказать / Отказать с причиной** (причина уходит агенту как follow-up).
   Режим настраивается: `self_change.approval = manual | auto`.
4. Одобрение → merge в `main` → агент вызывает `self.rebuild`: супервизор делает снапшоты
   активных сессий, `git pull`, при изменении `Dockerfile`/зависимостей — пересборка образа
   (супервизор имеет доступ к docker на хосте, агент — только через этот тул), preflight
   (compileall, импорт, конфиг, smoke), запуск. Провал → откат на последний тег `good/<n>`,
   лог ошибки в General. Сессии возобновляются из снапшотов.
5. `/rollback [n]` — одна команда. Всё, что должно пережить пересборку и не попасть в git
   (секреты, sqlite, workspaces, установленные вручную артефакты) — на volume `/srv/state`.

Ядро обновляется так же: `protocore-exp` имеет `upstream` на community; агент делает
merge апстрима в ветку, PR, тесты ядра — тот же путь.

## 5. Провайдеры моделей

Базовый класс `OpenAICompatibleProvider` (SSE `chat/completions` → `ProviderDelta`),
от него три конфигурации: **DeepSeek** (`api.deepseek.com`, по умолчанию `deepseek-flash` (= DeepSeek-V4.1-Flash; прежние имена `deepseek-v4-flash` принимаются и обслуживаются той же моделью),
thinking on/off + `reasoning_effort`, по умолчанию on/medium),
**OpenRouter**, **vLLM** (любой самохостный OpenAI-совместимый эндпоинт). Плюс `IProviderChain`
для fallback-цепочки (DeepSeek → OpenRouter). Смена модели — `/model` и из Mini App,
на лету (`model_changed` событие ядра). Новый провайдер = один файл в `providers/` —
именно такую задачу агент должен уметь выполнить сам.

Известный риск: DeepSeek склонен возвращать JSON в fenced-блоках — в структурных
вызовах (`complete_structured`) нужен парсер с разбором ``` ``` ```.

## 6. Инструменты (стартовый набор)

`exec` (bash, без ограничений, с потоковым выводом в статус), `read`, `write`, `edit`,
`find`, `search` (rg), `web_fetch`, `web_search` (сменные бэкенды: SearXNG по умолчанию, DuckDuckGo, платные API через key proxy), `send_file` (в текущий топик),
`ask_user`, `remember/recall/forget`, `spawn_task` (новая сессия/топик), `self.restart`,
`self.rollback`, `self.rebuild`, `schedule` (создать/изменить/удалить задачу планировщика,
с прикреплением файлов из текущего workspace), `skill` (загрузка SKILL.md). Тулы — обычные `@tool`-функции в
`daedalus/tools/`, регистрируются автосканом каталога, чтобы «добавь себе тул» =
«создай файл».

## 6a. Файлы и follow-up

Любое сообщение в топик во время работы агента — это follow-up (ядро: `follow_up_queued` /
`steer_queued`), в том числе на старте. Поддерживаются текст, текст+файл (caption), файлы
(по одному и альбомом), картинки. Файл сохраняется в `/srv/workspaces/<session>/inbox/`,
агенту передаётся текст сообщения и список путей; картинки дополнительно уходят в модель как
image-блоки, если провайдер их принимает. Входящие склеиваются окном ~1.5 с (Telegram режет
длинный ввод). Скачивание идёт через **локальный Bot API server** (лимит 2000 МБ вместо 20).

## 6b. Планировщик

Таблица `schedules` в SQLite: cron-выражение или одноразовое время, промпт, прикреплённые
файлы (копируются из workspace создателя в момент создания), модель, флаг `recurring`.
Повторяющаяся задача имеет **свой постоянный workspace** `/srv/workspaces/sched-<id>/`;
после каждого срабатывания агент пишет `SUMMARY.md` (ядро даёт cross-run summary в
`session_memory`), который подаётся в контекст следующего запуска. Каждое срабатывание —
отдельная сессия и топик `[cron] <имя> #n` (или один топик на задачу, настраивается).
Агент создаёт задачи сам тулом `schedule`; оператор — командой `/schedule` и из Mini App.

## 6c. Расходы и баланс

Из ответа провайдера сохраняется всё, что он отдаёт (prompt/completion/cache-hit/miss
токены, reasoning-токены, стоимость по прайсу) по каждому вызову, агрегируется по сессии,
дню, задаче. В Mini App — вкладка Usage. Отдельный **монитор баланса**: раз в минуту
`GET /user/balance` DeepSeek; настраиваемый список порогов (`[5.0, 2.0, 0.5]` USD), при
пересечении вниз — уведомление в General; повтор только после пополнения выше порога.

## 7. Стек

- Python 3.12, `uv`, **aiogram 3** (long polling — публичный URL для бота не нужен).
- FastAPI внутри того же процесса: Mini App статика + JSON API + валидация `initData`
  (HMAC-SHA256 от `bot_token` с ключом `"WebAppData"`, проверка `auth_date`).
- Mini App: Vite + React 19, мобильный-первый, **в стиле Grok Bot**: сессии как «боты» с
  постоянной идентичностью, аватар, чей статус (idle/thinking/working/waiting/blocked/done)
  передаётся анимацией, единая лента из сообщений, системных событий и карточек-виджетов,
  тёмная тема по умолчанию.
- SQLite (WAL) для сессий/ранов/событий; блобы на диске.
- HTTPS для Mini App: любой reverse proxy с TLS на хосте (или туннель) перед портом бота;
  Telegram требует валидный сертификат.
- Локальный Bot API server (`telegram-bot-api`) — отдельный контейнер в compose, обязателен.
- `gh` в образе, `GITHUB_TOKEN` с volume.

## 8. Безопасность (граница — вокруг контейнера, а не внутри)

- whitelist Telegram user_id (только владелец);
- операторские команды и `/panic` — до цикла агента;
- лимиты расходов — в супервизоре;
- `GOVERNANCE.md` и `/opt/launcher` закрыты для записи тулами (path policy ядра);
- PAT только на `daedalus` и `protocore-exp`; docker.sock в контейнер агента не монтируется — образ
  пересобирает отдельный контейнер `rebuilder` по триггер-файлу от супервизора;
- `/opt/launcher` и `GOVERNANCE.md` смонтированы read-only — менять их можно только через PR;
- дневной лимит расходов задаётся в env супервизора (`USD_PER_DAY`), не в `config.toml`;
- диффы self-change видны оператору до/после применения; fingerprint диффа до и после
  ревью (идея Ouroboros).

## 9. Порядок сборки (не «версии», а порядок — цель одна, финальная)

1. Хост-слой: провайдеры, тулы, SQLite-хранилища, запуск одного `QueryEngine` из CLI.
2. Супервизор + Dockerfile + self.restart с preflight и откатом.
3. Telegram: топики-сессии, статус-сообщение, файлы, AskUser-кнопки, операторские команды.
4. Mini App: сессии, транскрипт, диффы, логи, настройки.
5. Первая self-develop задача, поставленная через бота: «добавь себе провайдер N».
